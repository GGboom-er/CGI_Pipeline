# CGI Pipeline Operator

CGI owns DCC execution. The current MCP schema owns outer arguments; API/workflow metadata owns business inputs. Do not infer parameters from a tool name or abbreviated usage text.

## Select and bind

- Reuse the task’s verified storage binding. For a new classified YSJ asset task, set workspace_project to ysj/blenderToMaya, ysj/RigUpdate or ysj/proxyRig according to the actual job; business project remains ysj. Generic tool/governance tasks use default. A changed category requires the registered relocation and task rebind, not a second workspace or an ad hoc move.

- Proxy Rig creation, batch continuation or local revision: load the CGI-owned project method [proxy-rig](Y:/GGbommer/scripts/Notes/Tools/_managed/cgi_pipeline/.agents/skills/proxy-rig/SKILL.md). It owns stage order, conditional handling and delivery decisions; this Skill still owns transport, observation and result recovery. Ordinary Maya operations, file statistics and USD/GPU Cache/Reference tests stay on their existing route. This is initial routing only: when proxy-rig already selected this Skill for shared operations, reuse the loaded instructions and do not re-enter the project method.

- Unknown API: select with `list_apis` facet filters/`search` (rows carry only api_id, access, modes and a one-line summary; page with `cursor` rather than listing everything), read `api_help` for effects, inputs and verification, then bind every `mcp_call_template.requires_binding` field using real task/session data. Nulls are placeholders. Retain `catalog_version` and the current client's tool schema.
- Known contract: call `execute_api` directly with `expected_catalog_version`. Refresh once on `CATALOG_VERSION_STALE`; this version covers API contracts, not tool schemas or live sessions. Rediscover the tool schema after client/server replacement. Fix only the reported field or prerequisite.
- For foreground queries or view operations needing no file workspace, keep the matching `business_task_id` and project, and omit `workspace_id`: the existing TASK_LINK path retains audit/results without repeatedly rendering workspace reports. Keep the explicit workspace for task image/file outputs or when the API requires it; do not drop both task selectors.
- Literal same-DCC calls: `execute_batch`; `atomic=true` stops at first failure, false continues. Inspect each receipt and `rolled_back`; disk/external effects are not guaranteed to roll back.
- Registered composition: `list_workflows` supplies inputs and a call template for `pipeline_execute_workflow`. Bind external inputs or their declared source alternatives (project + asset resolution / recorded workspace source); runtime supplies run/info directories. Missing inputs must be corrected before execution.
- Alembic scene export: `.blend` → `blender.asset.blender_export_abc`; `.ma/.mb` → `maya.asset.maya_export_abc`. Read current help and use the registered staging/open contract. Do not recreate retired `create_worker/run_skill` wrappers.

## Observe and verify

Choose the existing observation API for the question, reading its current effects and prerequisites:

- Background window observation: `pipeline.window.discover` finds explicit window/process identities, then `pipeline.window.capture` captures the selected identity. Use the actual application's executable basename for ordinary software as well as DCCs; no DCC scene is required. Bind identities from discovery, rather than guessing the active window or an ambiguous title. Default capture changes no window state. A window image includes its content even when occluded; use desktop scope to know what is actually visible on a screen.
- Current monitor/desktop observation: reuse discovery with `include_monitors=true`, then the same capture API with `scope=desktop`. Bind its optional `expected_monitors` to the complete discovered topology, and choose all monitors or explicit `monitor_indices`. The API returns individual PNGs and, by default, a composite retaining negative screen coordinates and portrait displays. Frames are sequential and carry individual times; transparent composite gaps are outside the physical displays. Open the images before judging each screen. No activation, maximization or window switching is needed.
- Minimized window branch: first use an already available application/browser-native content or image interface if it answers the question. If window pixels are needed and existing authorization permits reversible show-state changes, use the same capture API's explicit `minimized_policy=restore`: non-activating display, brief frame collection, capture, then original placement and minimized-state restoration. Check `window_state.performed/restored/error`; do not treat capture success alone as restoration success. It may temporarily become visible, so do not promise invisible operation. An explicit user prohibition on restoring/changing window state remains binding. If user activation or movement conflicts with restoration, preserve that action and inspect the reported state instead of forcing focus or blindly retrying.
- Use existing Computer Use when accessibility/control evidence or authorized interaction is needed. Do not launch test apps, type or move windows merely to prove observation. For blank/loading captures, inspect what is visible, use the native page/application state when available and make only a targeted follow-up that can change the conclusion; blank pixels do not prove absent content.
- Maya viewport and scene/view context: use `maya.asset.maya_capture_viewport` with an explicitly chosen viewport scope and visible panel from its help and current session. Read effects before choosing scope: the legacy whole-window scope raises and activates Maya, so it does not satisfy a background/no-interruption request. Viewport capture may refresh/evaluate Maya. Keep the current camera, frame and display conditions unless changing the view was authorized.
- Known Maya target: reuse its verified full DAG path/UUID and query only the data needed. For a closer view, use the existing `maya_select_objects` API with explicit panel and `frame=true`, retaining its `view_restore`. Authorized isolate viewing uses Maya's native `isolateSelect` through the existing code API when no registered isolate operation exists; preserve the prior enabled state, membership and selection, then restore them. Prefer moving/framing the camera or isolating the target over enumerating every mesh or vertex to identify it.
- Unknown Maya image region: acquire an ordinary viewport PNG, open it, then use `maya.scene.viewport.pick` with `mode=native`, explicit panel and original top-left pixel indices. Pass the ordinary capture's `output.observation` as optional `expected_view` to check its cheap context. Inspect all native candidates and exact instance paths; do not choose the first ambiguous hit. A visible area with no native hit may be excluded by Maya's display/selectability rules; inspect those rules or isolate a known target rather than declaring the model absent.
- Use `mode=verified` with a grounded original PNG only when saved-image/full polygon consistency or its strict edit guard is actually needed. Native hits describe the current control's candidates; they do not certify historical PNG, depth order, arbitrary shader pixels or semantic labels, and are not a strict edit-guard token. Do not make full-scene snapshots or geometry hashes a prerequisite for ordinary viewing, identification or editing.
- Scene structure or numerical evidence: combine existing scene, hierarchy, object, attribute, graph or measurement read APIs as needed. A connection graph does not prove evaluated behavior; a screenshot does not prove hidden geometry, topology, deformation accuracy, material settings or final rendered quality. Houdini window observation does not imply Houdini scene/edit APIs exist; inspect the catalog before claiming support.

Open the returned PNG with the client's image-view tool before making a visual judgment. Pixels already rendered in the conversation can be examined directly; a file path, successful receipt or image dimensions alone do not count as seeing the image. If pixels cannot be displayed or needed detail is absent, report NEED_VIEW or the precise unknown instead of guessing. Record the actual image path and available window/scene/view/frame/capture context; distinguish what is visible, what other queries establish, and what remains inference or unverified.

For authorized edits, retain relevant read evidence and a before image, apply the approved change through the registered API/workflow, then inspect an after image under comparable view/frame/display conditions and run the relevant data checks. A distant whole-window image cannot validate a tiny shape change; obtain an authorized closer view or leave that detail unverified. Do not change or save a scene merely to make a screenshot look better.

Report focus only from meaningful observations. A zero foreground handle or missing intervals leaves focus behavior unknown, even when a receipt says the before/after values match. Capture success is not a promise of uninterrupted focus, scene freshness or compatibility with every DCC. On capture failure recover the same task and inspect its diagnostics; do not silently substitute a disruptive capture method or present an older image as a new observation.

## Execute and recover

- Foreground uses `execute_api`, `execution_mode="foreground"` and an explicit verified `foreground_port`; it operates the selected resident scene. Use the user's actual project for authorized incremental work. Isolation is only required by the requested operation or its contract, not by every DCC task.
- Keep `wait=true`; the server caps the wait below the client tool timeout and returns `PROGRESS` with the `task_id` when it is reached. Recover with `get_task_result(task_id)`, which itself waits server-side for a terminal state, so call it again only after it returns `PROGRESS`; never poll in a tight loop. `wait_sec=0` reads the current state at once. A client timeout or unknown write outcome is never a reason to resubmit.
- Results over 4 KiB return a summary: status, errors, artifacts, small output fields (large ones replaced by their size/shape) and `receipt_ref`. Act on the summary when it answers the question; pass `detail=true` (to the execution call or `get_task_result`) only when the omitted output is actually needed.
- Pass stable `business_task_id` + `project` for business grouping; retain returned `workspace_id` for exact recovery. File-based operations reuse the business workspace; no-file UE/Pipeline and unbound foreground calls may only record the association. Each call retains its own `task_id`.
- Continue resident work with `scene_action="continue"`; do not repeat discovery, staging, scene opening or a whole workflow for a follow-up query. On `WORKSPACE_SCENE_UNAVAILABLE`, restore from a known saved `source_path` using `scene_action="open"` where supported. Save important changes before switching tasks/restarting; do not replay earlier writes.
- Protected sources remain read-only; background saves follow their workspace contract. Python path guards are cooperative checks, not operating-system isolation. Use the contract's approved output paths.
- Success: report actual output and any `report_path`. `PARTIAL` is finished but incomplete; report gaps. `ERROR`/`BLOCKED`/`AUDIT_FAILED` and failed workflows require the returned reason/checklist. `NEEDS_ATTENTION` requires the actual missing decision. `SUBMITTED`/`PROGRESS` require recovery of the same task. `isError=false` alone never proves success.

## Lifecycle and ownership

CGI starts and reuses its serial queue and workers; do not manually manage Redis/Celery for ordinary work. For an authorized task, launch or normally close/restart the target DCC using verified executable/project paths. Prefer a registered lifecycle API; otherwise use the host launcher and application's normal close. Reuse matching sessions, preserve unsaved work, never force-terminate unrelated sessions, then discover/verify the session. Scene operations remain through CGI, without client raw sockets or legacy named tools.
